GrubPac API Documentation — Architecture & Flow

Where files live (local Git repos vs hosted websites), real folder structure aligned to GrubAdmin-Backend, and the end-to-end update flow on every release.

GrubAdmin-Backend · GrubPac-API-Docs · docs.grubpac.com · Internal Reference

1. What Lives Where

Three separate places — local repositories, the API server, and the documentation website.

Local — Git repositories (your machine / GitHub)

  • GrubAdmin-Backend — API source code + generated OpenAPI specs
  • GrubPac-API-Docs — documentation portal content (guides, portal config)
  • GrubDelivery-Frontend — delivery portal UI (consumes APIs; does not host docs)

Hosted — live servers (cloud / production)

  • api.grubpac.com — running GrubAdmin-Backend (/api/v1/*)
  • docs.grubpac.com — documentation website (Mintlify / Redocly)
  • delivery.grubpac.com — running GrubDelivery-Frontend
Item Location URL / path Purpose
API handlers, validators, DB logic Git — local GrubAdmin-Backend/src/ Backend implementation
OpenAPI specification files Git — local GrubAdmin-Backend/openapi/ to be added Machine-readable API contract; generated from code
Integration guides, changelog Git — local GrubPac-API-Docs/guides/ new repo Human-written documentation pages
Postman collection Git — local GrubAdmin-Backend/postman/ QA / dev testing; auto-exported from OpenAPI in CI
API Reference pages Hosted website docs.grubpac.com/reference/* Auto-generated from OpenAPI — not stored as hand-written files
Guide pages on portal Hosted website docs.grubpac.com/guides/* Rendered from GrubPac-API-Docs MDX files on publish
Live API endpoints Hosted server api.grubpac.com/api/v1/* Deployed GrubAdmin-Backend — what apps actually call
Delivery portal UI Hosted server delivery.grubpac.com GrubDelivery-Frontend — proxies to API; separate from docs site
Key distinction: The documentation website (docs.grubpac.com) is not inside GrubAdmin-Backend or GrubDelivery-Frontend. It is a separate hosted portal built from the GrubPac-API-Docs Git repo + synced OpenAPI files.

4. End-to-End Flow — Every Time APIs Change

What happens on each code change, from local development to live documentation and API.

flowchart TB subgraph LOCAL["LOCAL — Git repositories"] A["Developer edits\nGrubAdmin-Backend\nhandlers / validators"] B["PR review & merge\nto main branch"] C["GrubPac-API-Docs\nguides / changelog edits"] end subgraph CI["CI/CD — runs on merge"] D["Generate OpenAPI specs\nhono-openapi → openapi/*.yaml"] E["Bundle → openapi.bundle.yaml\nExport Postman collection"] F["Sync bundle to\nGrubPac-API-Docs repo"] G["Deploy GrubAdmin-Backend\nto API server"] end subgraph HOSTED["HOSTED — live services"] H["api.grubpac.com\n/api/v1/*"] I["docs.grubpac.com\nMintlify rebuilds portal"] J["delivery.grubpac.com\nGrubDelivery-Frontend"] end subgraph USERS["Consumers"] K["Engineers / QA\nread docs, use Postman"] L["Frontend / mobile\ncall live APIs"] end A --> B B --> D --> E --> F B --> G C --> I F --> I G --> H I --> K H --> L J -->|"proxy /api/v1/*"| H K -->|"test against"| H
1

Developer changes API code

Modify handlers or Zod validators in GrubAdmin-Backend. Run locally against dev API server.

LOCAL → GrubAdmin-Backend/src/modules/
2

Pull request merged to main

Code review complete. CI pipeline triggers on merge.

GitHub → GrubAdmin-Backend
3

CI generates OpenAPI specification

hono-openapi reads routes and Zod schemas. Outputs per-module YAML files and a merged bundle.

CI → GrubAdmin-Backend/openapi/
4

CI syncs spec to docs repository

openapi.bundle.yaml and Postman collection pushed to GrubPac-API-Docs (or same pipeline artifact).

CI → GrubPac-API-Docs/openapi/
5

CI deploys backend to API server

Existing deployment pipeline publishes new API behaviour to production/staging.

HOSTED → api.grubpac.com
6

Documentation portal rebuilds automatically

Mintlify / Redocly detects Git change in GrubPac-API-Docs. API Reference pages regenerate from the new OpenAPI bundle.

HOSTED → docs.grubpac.com
7

Teams consume updated documentation and APIs

Engineers and QA use docs.grubpac.com and Postman. GrubDelivery-Frontend and mobile clients call the updated api.grubpac.com endpoints.

docs.grubpac.com + api.grubpac.com + delivery.grubpac.com
After initial setup, steps 3–6 run automatically on every merge. No manual doc updates for endpoint reference pages. Guide pages (auth, environments) are updated only when the team edits GrubPac-API-Docs/guides/.
