GrubPac API Documentation — Architecture & Flow

Where files live (local Git repos vs hosted websites), real folder structure aligned to GrubAdmin-Backend, and the end-to-end update flow on every release.

GrubAdmin-Backend · GrubPac-API-Docs · docs.grubpac.com · Internal Reference

1. What Lives Where

Three separate places — local repositories, the API server, and the documentation website.

Local — Git repositories (your machine / GitHub)

  • GrubAdmin-Backend — API source code + generated OpenAPI specs
  • GrubPac-API-Docs — documentation portal content (guides, portal config)
  • GrubDelivery-Frontend — delivery portal UI (consumes APIs; does not host docs)

Hosted — live servers (cloud / production)

  • api.grubpac.com — running GrubAdmin-Backend (/api/v1/*)
  • docs.grubpac.com — documentation website (Mintlify / Redocly)
  • delivery.grubpac.com — running GrubDelivery-Frontend
Item Location URL / path Purpose
API handlers, validators, DB logic Git — local GrubAdmin-Backend/src/ Backend implementation
OpenAPI specification files Git — local GrubAdmin-Backend/openapi/ to be added Machine-readable API contract; generated from code
Integration guides, changelog Git — local GrubPac-API-Docs/guides/ new repo Human-written documentation pages
Postman collection Git — local GrubAdmin-Backend/postman/ QA / dev testing; auto-exported from OpenAPI in CI
API Reference pages Hosted website docs.grubpac.com/reference/* Auto-generated from OpenAPI — not stored as hand-written files
Guide pages on portal Hosted website docs.grubpac.com/guides/* Rendered from GrubPac-API-Docs MDX files on publish
Live API endpoints Hosted server api.grubpac.com/api/v1/* Deployed GrubAdmin-Backend — what apps actually call
Delivery portal UI Hosted server delivery.grubpac.com GrubDelivery-Frontend — proxies to API; separate from docs site
Key distinction: The documentation website (docs.grubpac.com) is not inside GrubAdmin-Backend or GrubDelivery-Frontend. It is a separate hosted portal built from the GrubPac-API-Docs Git repo + synced OpenAPI files.

4. End-to-End Flow — Every Time APIs Change

What happens on each code change, from local development to live documentation and API.

1

Developer changes API code

Modify handlers or Zod validators in GrubAdmin-Backend. Run locally against dev API server.

LOCAL → GrubAdmin-Backend/src/modules/
2

Pull request merged to main

Code review complete. CI pipeline triggers on merge.

GitHub → GrubAdmin-Backend
3

CI generates OpenAPI specification

hono-openapi reads routes and Zod schemas. Outputs per-module YAML files and a merged bundle.

CI → GrubAdmin-Backend/openapi/
4

CI syncs spec to docs repository

openapi.bundle.yaml and Postman collection pushed to GrubPac-API-Docs (or same pipeline artifact).

CI → GrubPac-API-Docs/openapi/
5

CI deploys backend to API server

Existing deployment pipeline publishes new API behaviour to production/staging.

HOSTED → api.grubpac.com
6

Documentation portal rebuilds automatically

Mintlify / Redocly detects Git change in GrubPac-API-Docs. API Reference pages regenerate from the new OpenAPI bundle.

HOSTED → docs.grubpac.com
7

Teams consume updated documentation and APIs

Engineers and QA use docs.grubpac.com and Postman. GrubDelivery-Frontend and mobile clients call the updated api.grubpac.com endpoints.

docs.grubpac.com + api.grubpac.com + delivery.grubpac.com
After initial setup, steps 3–6 run automatically on every merge. No manual doc updates for endpoint reference pages. Guide pages (auth, environments) are updated only when the team edits GrubPac-API-Docs/guides/.

7. OpenAPI — What It Is and What We Use

OpenAPI is not a separate product. It is the standard file format that sits between backend code and the documentation website.

OpenAPI is a machine-readable API contract — a YAML or JSON file that describes every endpoint, request field, response schema, and authentication rule in a structured format that tools can read and render automatically.

Three things we use from OpenAPI

# What What it means Where
1 OpenAPI 3.1
the format		 The standard type of file we store — .yaml or .json describing all API details GrubAdmin-Backend/openapi/
2 hono-openapi
the generator		 Reads Hono routes and Zod validators and auto-writes the YAML files. Endpoints are not typed by hand. GrubAdmin-Backend codebase + CI
3 Mintlify / Redocly
the reader		 Reads the OpenAPI file and builds the documentation website with navigation, search, and code samples docs.grubpac.com

Who interacts with OpenAPI

RoleInteractionOpens YAML directly?
Backend developerWrites handlers and Zod validators as today; generator updates YAML on buildNo
CI pipelineBundles YAML files, exports Postman, syncs to GrubPac-API-DocsYes (automated)
Docs platformReads YAML, renders API Reference pages on docs.grubpac.comYes (automated)
Frontend / QA / new hiresReads docs.grubpac.com and Postman collectionNo
OpenAPI is not a running server. It does not replace GrubAdmin-Backend. It is the blueprint file that the documentation platform reads to build and maintain the API Reference section.

8. Enterprise Alignment

How this approach compares to API documentation programs at Stripe, Microsoft, Uber, and comparable platforms.

Standard enterprise pattern vs our plan

Layer Enterprise standard Our plan Aligned?
API contract Machine-readable spec (OpenAPI) as single source of truth OpenAPI 3.1 YAML in Git Yes
API Reference docs Auto-generated from spec — not maintained in Word or Excel hono-openapi → YAML → Mintlify / Redocly Yes
Developer portal Hosted site with search, access control, versioning docs.grubpac.com Yes
Integration guides Human-written pages for auth, environments, workflows GrubPac-API-Docs/guides/ Yes
CI/CD sync Spec regenerated on every merge; docs stay in sync with deployed API GitHub Actions on merge to main Yes
Testing artefact Postman collection or equivalent exported from OpenAPI postman/grubpac-api.collection.json Yes

Where large enterprises differ (normal variation)

Area Large enterprise Our setup Impact
Portal platform Often Redocly, Backstage, or custom internal portal Mintlify or Redocly Same category of tool; ours is appropriate at our scale
Spec generation Built into framework (.NET OpenAPI, Google protobuf + transcoding) hono-openapi from Hono + Zod Same principle — framework-native generation
Repository layout Monorepo or separate docs repo depending on org Separate GrubPac-API-Docs repo Valid and common; keeps docs lifecycle independent
Audience Often external partners plus internal teams Internal portal (SSO) Simpler access model; same documentation architecture
Reference examples Stripe, Microsoft, Uber publish OpenAPI in GitHub We publish OpenAPI in GrubAdmin-Backend Git Identical pattern

What top enterprises do not do

Anti-patternWhy it fails at scaleOur approach
Hand-write hundreds of endpoints in Word / Excel Docs diverge from deployed API within weeks Auto-generated from code via hono-openapi
No machine-readable spec No automated portal, no reliable Postman export, no CI validation OpenAPI 3.1 as canonical contract
Swagger UI as the entire documentation program Functional but insufficient for search, guides, SSO, changelog Full portal via Mintlify / Redocly
Manual doc updates after each API release Human error; reference pages fall behind production CI regenerates spec and triggers portal rebuild on merge

Conclusion

The architecture in this document — OpenAPI file (auto-generated) → CI → developer portal — is the industry standard. Tool names differ between organisations; the pattern does not. Our plan is aligned with how Stripe, Microsoft, Uber, and comparable platforms structure API documentation programs.
