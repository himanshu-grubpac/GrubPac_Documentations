1. The 6 Tools — What Each One Does

H3 Geo Indexing Engine

Built by: Uber | Open Source (Apache 2.0) | Language: C core, JS/Python bindings | npm: h3-js
H3 is a hexagonal grid system created by Uber for their ride-sharing platform. It takes any GPS coordinate on Earth (like 25.2048, 55.2708) and maps it to a hexagon cell ID (like 8a2a1072b59ffff). Every location on the planet falls inside one hex. Instead of comparing raw lat/lon numbers for every query, you just compare cell IDs — which is instant. Uber built this because they needed to match millions of riders and drivers by location in real time. We use it the same way — to quickly answer "what is near this point?" without scanning every record in the database.
Use for: fast nearby lookups, heatmap visualization, geofence pre-check, movement paths, incident clustering, hotspot analytics, patrol coverage tracking.

PostGIS Exact Geometry Engine

Built by: OSGeo Foundation (Refractions Research originally) | Open Source (GPL 2.0) | Extension for PostgreSQL | Used by: NASA, USGS, European Commission, French IGN
PostGIS is the industry standard spatial extension for PostgreSQL. It adds geography and geometry data types — so you can store real shapes like points, polygons, and lines directly in the database. It answers exact questions: "Is this vehicle point inside this restricted zone polygon?" or "Exactly how many meters apart are these two locations?" This is the same tool used by government agencies worldwide when they need legally defensible, meter-accurate geographic calculations. We already use PostgreSQL — PostGIS is just an extension we enable on top of it. No new database needed.
Use for: exact polygon containment (legal evidence), camera FOV polygons, precise distance calculations, geofence boundary validation, route geometry storage, evidence boundary proof.

Redis Realtime Memory Cache

Built by: Redis Ltd (Salvatore Sanfilippo originally) | Open Source (BSD 3-Clause) | Already in our stack | Used by: Twitter, GitHub, Uber, Instagram
Redis is an in-memory data store — it keeps data in RAM instead of on disk, which makes reads and writes extremely fast (microseconds, not milliseconds). We already use Redis in GrubData for rate limiting, RBAC caching, and tenant feature flags. For geo features, we extend its use: instead of hitting the database every time someone asks "where are all active drivers right now?", we keep the latest position of every driver in Redis. It auto-expires old data — if a driver stops sending GPS pings for 60 seconds, their entry disappears automatically. No cleanup needed.
Use for: live driver positions, cell-to-driver index ("which drivers are in hex cell X?"), online/offline detection, realtime nearby search — all under 1 millisecond.

Valhalla Road Network Intelligence Engine

Built by: Mapzen (now maintained by community + Microsoft) | Open Source (MIT License) | Self-hosted Docker container | Uses OpenStreetMap road data
Valhalla is an open-source routing engine that understands actual roads. H3 and PostGIS only know about coordinates — they have no idea that there's a highway, a one-way street, or a water canal between two points. Valhalla loads the entire road map (from OpenStreetMap) and can answer: "What's the fastest road route from A to B?", "Snap these noisy GPS points to the nearest real road", and "Which areas can a vehicle reach from this point in 5 minutes?" We run it as a Docker container alongside our backend. For Dubai, we load the UAE road extract from OpenStreetMap. Alternative: OSRM (by Project OSRM / MapBox) — similar but Valhalla has better map-matching and isochrone APIs.
Use for: GPS-to-road snapping, real drive-time ETA, best route calculation, route deviation detection, road-aware dispatch, suspect reachable area estimation.

PostgreSQL Main Database (Already in System)

Built by: PostgreSQL Global Development Group | Open Source (PostgreSQL License) | Already our primary database | Used by: Apple, Instagram, Spotify, Reddit
PostgreSQL is the main database behind GrubData. It already stores all our tenants, users, roles, boxes, search jobs, results, audit logs, video requests, saved videos — everything. We already use the cube and earthdistance extensions for basic geo distance queries. PostGIS is another extension that upgrades our geo capabilities massively. No migration to a new database — we just add the extension to what we already have.
Already used for: all GrubData data. PostGIS extension enables spatial queries on the same database.

AWS S3 Evidence Storage (Already in System)

Built by: Amazon Web Services | Commercial cloud service | Already integrated | Stores all GrubData video and image evidence
AWS S3 is our cloud storage for video clips, face images, ANPR snapshots, and all raw media evidence. GrubPac boxes sync their recorded video to S3 (30-day cloud retention). None of the geo features change how S3 works — geo operates on metadata (coordinates, timestamps) not on the media files themselves. S3 stays exactly as it is.
Already used for: video and image evidence storage. No changes needed for geo integration.

3. Live Driver Tracking H3 Redis New

What it is: Track all active drivers and vehicles in realtime on the operator dashboard.

Example: Every patrol vehicle sends its GPS, speed, and heading every 2 seconds. The dashboard shows all of them live on the map.

How it works: GPS arrives → H3 converts lat/lon to a hex cell → Redis stores "driver 91 is in cell X" with a 60-second expiry. If the driver stops sending pings, they auto-disappear. Frontend polls Redis through the API to show live pins.

Where in GrubData: New telematics endpoint. Feeds real data into the existing behaviorMonitoring.activeDrivers dashboard field that currently uses placeholder data.

    A["Vehicle sends GPS\nevery 2 seconds\nlat, lon, speed, heading\ndriver ID, timestamp"] --> B["Telematics API\nreceives the ping"]
    B --> C["H3 converts\nlat/lon → hex cell\n~175 meter hexagon"]
    C --> D["Redis stores\ndriver:91 → current position\ncell:abc → driver 91\nExpires in 60 seconds"]
    C --> E["PostgreSQL stores\ndriver_pings table\nfor historical audit trail"]
    D --> F["Dashboard API reads\nall active drivers\nfrom Redis"]
    F --> G["Frontend shows\nlive driver pins\non the map"]

    style C fill:#E8F5E9
    style D fill:#FFF8E1
    style E fill:#E3F2FD
Library cost: H3 = $0 (open source, runs in-process). Redis = $0 additional (already in our stack).
Without this: At 1M drivers sending GPS every 2 seconds = 500,000 queries/sec hitting PostgreSQL directly. You'd need a massive DB cluster ($5,000–$15,000/month) just for live position queries, and it still wouldn't be real-time.
With this: Redis handles 500K reads/sec on a single $50–$200/month instance. H3 cell conversion is pure math — zero network cost, runs in microseconds in Node.js memory. PostgreSQL only gets batch writes for history (100x less load).
Efficiency gain: ~95% reduction in database load. Live queries go from 50–200ms (DB) to <1ms (Redis). System part affected: dashboard.service.ts behavior monitoring, new telematics endpoint.
At scale (1M boxes): Saves roughly $10,000–$14,000/month in database compute costs alone.

4. Nearby Driver Lookup H3 Redis New

What it is: Answer the question: "Which drivers are near this incident right now?"

Example: An explosion alert comes in. You need the nearest responders immediately.

Without H3: You'd run PostGIS exact distance against every driver in the database. Heavy, slow.

With H3: Incident is in cell ABC. Use gridDisk(ABC, 3) to get all nearby cells. Ask Redis: "who is in those cells?" Instant answer. Under 1 millisecond.

Where in GrubData: New dispatch feature. Uses the same Redis cell index from live driver tracking.

    B --> C["H3 gridDisk\ngets 37 neighboring\ncells around incident"]
    C --> D["Redis lookup\nall drivers in those\n37 cells\nunder 1 millisecond"]

    style B fill:#E8F5E9
    style C fill:#E8F5E9
    style D fill:#FFF8E1
Library cost: $0. Same H3 + Redis already running for live tracking.
Without this: To find nearby drivers you'd run ST_DWithin against every active driver row in PostgreSQL. With 1M drivers, that's a full spatial scan every time someone asks — 500ms–2 seconds per query under load, plus heavy DB CPU.
With this: Redis SUNION on 37 cell keys = <1 millisecond. Zero database involvement. Even at 10,000 concurrent dispatch lookups, Redis handles it on a single node.
Efficiency gain: 500x–2000x faster response. System part affected: new dispatch endpoint, incident response workflow.
At scale (1M boxes): Enables real-time dispatch that would be physically impossible with database-only approach. Saves the cost of a dedicated PostGIS read replica ($500–$2,000/month).

5. ANPR Geo Correlation H3 Existing + Enhanced

What it is: ANPR = Automatic Number Plate Recognition. Each detection has a plate, camera, time, and location. H3 indexes the location so you can quickly find the same vehicle nearby or trace its movement.

Example: Plate DUB-1234 was seen at camera 3 at 10:15 AM. Later you want to know: "Was this plate seen anywhere nearby?" Search neighboring H3 cells instead of scanning every record.

Where in GrubData: The existing search worker already stores location in search_job_results.payload. We add an H3 cell column so these results become instantly searchable by geography. New plate_observations table for cross-search correlation.

Use cases: Stolen vehicle tracking, suspect movement, plate hotspot analysis, repeated sightings correlation.

    B --> C["Store in plate_observations\nplate + cell + timestamp\n+ camera + box"]
    C --> D["Later query:\nFind same plate nearby\nSearch neighboring cells\nCorrelate sightings"]
    D --> E["Result:\nPlate seen at 3 locations\nMovement path revealed\nTimeline reconstructed"]

    style B fill:#E8F5E9
    style C fill:#E3F2FD
Library cost: $0. H3 runs in-process. PostgreSQL column addition — no new service.
Without this: "Find same plate nearby" requires scanning every search_job_results row and computing distance for each one. With 10M+ results across all tenants, that's a multi-second sequential scan per query. At 1M boxes producing ANPR hits continuously, the table grows by millions of rows per day.
With this: Add h3_index_r9 column with a B-tree index. Query becomes WHERE h3_index = ANY($cells) — index lookup, returns in 2–5ms regardless of table size. Storage cost for the extra column: ~8 bytes per row.
Efficiency gain: Geo queries on ANPR results go from O(n) full scan to O(1) index hit. System part affected: search.worker.ts (write path), search results API (read path).
At scale (1M boxes): Prevents the need for a separate search/indexing service (like Elasticsearch for geo queries — $500–$3,000/month). Everything stays in PostgreSQL.

6. Face Movement Tracking H3 New

Example: Suspect face detected at Camera A (10:00), Camera B (10:15), Camera C (10:30). Each detection has a GPS location. H3 indexes each one. Query by face_id ordered by time = movement path.

Where in GrubData: Face search already uses AWS Rekognition and stores results. We add a face_observations table to log each detection with its H3 cell. Frontend draws the path on the map with a timeline.

Use cases: Suspect movement tracking, face correlation across boxes, path reconstruction, hotspot presence analysis.

7. Heatmaps H3 Existing + Enhanced

What it is: Visual density maps. Shows where things happen most — incidents, detections, patrols, ANPR hits.

Today: Dashboard heatmap uses lat.toFixed(3) string bucketing — crude rectangular grid, uneven, overlapping.

With H3: Data is already geo-bucketed into hex cells. Just GROUP BY cell, count events, render colored hexagons. Clean tessellation, no overlap, proper density visualization. Each hex covers equal area.

Where in GrubData: Replace logic in dashboard.service.ts getDashboardHeatmap function. Frontend renders hex polygons using cellToBoundary coordinates.

Use cases: Incident density, patrol coverage heatmap, face detection hotspots, ANPR hit concentration.

8. Geofencing H3 PostGIS New

What it is: Virtual restricted areas. Airport, government buildings, military zones. Any vehicle entering triggers an alert.

How it works: Admin draws a polygon on the map. System stores it as a PostGIS polygon AND converts it to a set of H3 cells. On every driver ping: first do a fast H3 check (is this cell in any zone's cell list?). Only if H3 says "maybe" do we run the expensive PostGIS exact containment check. Two-stage = fast + accurate.

Where in GrubData: New geo_zones table. Check runs inside the telematics ping handler. Alerts go to audit_logs + push notification.

Use cases: No-entry zones, patrol boundaries, restricted compound alerts, evidence area monitoring.

    C["Driver ping arrives\nH3 converts to cell"] --> D{"H3 fast check:\nis cell in any\nzone's cell list?"}
    D -->|"No match"| E["Not in any zone\nContinue normally"]
    D -->|"Possible match"| F["PostGIS exact check:\nST_Contains polygon, point\nPrecise boundary test"]
    F -->|"Outside"| E
    F -->|"Confirmed inside"| G["ALERT triggered\nAudit log entry\nPush notification\nDispatch response"]

    style D fill:#E8F5E9
    style F fill:#E3F2FD
    style G fill:#FFCDD2
Library cost: $0. H3 polygonToCells runs once at zone creation. PostGIS is a free PostgreSQL extension.
Without this: Every GPS ping (1M drivers × 0.5 pings/sec = 500K pings/sec) would need to run ST_Contains against every geofence polygon in PostGIS. With 500 zones, that's 250 million PostGIS operations per second. You'd need a cluster of dedicated PostGIS servers ($10,000–$30,000/month). Commercial geofencing APIs (Google Geofencing, HERE) charge $0.004–$0.01 per check = $1M+/month at this scale.
With this: H3 pre-check is a simple array lookup — eliminates 99% of pings instantly. PostGIS only runs on the 1% that actually might be inside a zone. 250M ops/sec drops to ~2.5M/sec, easily handled by existing DB.
Efficiency gain: 99% reduction in PostGIS operations. System part affected: telematics ping handler, audit_logs table, new geo_zones table.
At scale (1M boxes): Saves $10,000–$30,000/month in compute vs pure PostGIS approach. Saves $1M+/month vs commercial geofencing APIs.

10. Route Deviation H3 Valhalla New

What it is: Expected route vs actual route. Was the driver supposed to go A → B → C but actually went A → D → E?

How it works: Expected route is a set of H3 cells. Actual GPS pings get map-matched to real roads via Valhalla, then converted to cells. Cells in actual but NOT in expected = deviation detected.

Limitation: H3 alone gives approximate deviation. Valhalla adds road-accurate detection.

Where in GrubData: Combines telematics ping stream + Valhalla map-matching + cell comparison logic.

Use cases: Driver monitoring, delivery compliance, suspect vehicle tracking.

12. Multi-Resolution Zoom H3 New

H3 functions: cellToParent(cell, parentRes) and cellToChildren(cell, childRes)

What it is: Every H3 cell exists at multiple resolutions — like zooming in and out on a map. A resolution-5 hex covers a big area (about 250 km²). A resolution-9 hex covers a small area (about 0.1 km²). cellToParent takes a small cell and gives you the bigger cell it sits inside. cellToChildren does the reverse — gives you all the smaller cells inside a big one.

How we use it in GrubData: When the dashboard heatmap is zoomed out (city level), we use resolution 5 or 6 for broad clusters. When zoomed in (street level), we use resolution 9 for precise hotspots. Instead of re-querying the database at each zoom level, we just call cellToParent on the stored resolution-9 cells to roll them up to any coarser level on the fly. Same data, different zoom — no extra DB queries.

Where: Dashboard heatmap zoom handler. Also useful for analytics reports — "incidents per district" (res 5) vs "incidents per street" (res 9) from the same dataset.

flowchart LR
    A["User zooms out\non dashboard map"] --> B["Take stored res-9 cells\nfrom search results"]
    B --> C["H3 cellToParent\nconvert each to res-5\nbigger hexagons"]
    C --> D["Group by parent cell\nsum weights\nfewer, larger hexes"]
    D --> E["Frontend renders\nbroad city-level\nheatmap view"]

    style C fill:#E8F5E9
Library cost: $0. cellToParent is a pure bit-shift operation — runs in nanoseconds per cell.
Without this: Each zoom level on the heatmap would require a separate database query with different aggregation parameters. 5 zoom levels = 5 DB queries per dashboard load. At 1,000 concurrent operators, that's 5,000 DB queries per page view.
With this: Query DB once at finest resolution (res-9). Client-side cellToParent rolls data up to any zoom level instantly. 5 zoom levels = 1 DB query + 4 in-memory transforms (microseconds each).
Efficiency gain: 80% fewer DB queries for zoom interactions. System part affected: dashboard heatmap, analytics reports.
At scale (1M boxes): Reduces dashboard DB load by 4–5x. Saves PostgreSQL read capacity for search jobs instead of repeated heatmap recomputes.

13. Path Between Locations H3 New

H3 function: gridPathCells(startCell, endCell)

What it is: Given two H3 cells (point A and point B), this function returns all the hex cells that form a straight-line path between them. Think of it like drawing a line on a hex grid and getting every hex the line passes through.

How we use it in GrubData: When we track a suspect's face or plate across two camera locations, gridPathCells gives us the approximate cells the suspect traveled through between those sightings. We can then check if any other cameras or boxes exist in those intermediate cells — to find additional evidence we might have missed. Also useful for showing expected travel corridors on the map.

Where: Face/ANPR movement tracking — filling gaps between known detection points. Also useful for route planning visualization.

flowchart LR
    A["Suspect seen at\nCamera A cell\nthen Camera C cell"] --> B["H3 gridPathCells\nA → C\nreturns all cells\nalong the path"]
    B --> C["Check: any other\ncameras or boxes\nin those middle cells?"]
    C --> D["Found Camera B\nin the path!\nPull its video too"]

    style B fill:#E8F5E9
Library cost: $0. gridPathCells is an in-memory computation.
Without this: To find cameras between two detection points, you'd query every box in the database and compute distance to every point along an interpolated line. With 1M boxes, that's a full spatial scan per path query.
With this: gridPathCells returns ~10–50 cells between two points. Query becomes WHERE h3_index = ANY($pathCells) — index lookup, returns in 1–3ms.
Efficiency gain: Enables automatic evidence discovery between known detection points. System part affected: face/ANPR movement tracking API, search result correlation.
At scale (1M boxes): Finds missed evidence automatically — cameras the operator didn't think to check. Increases investigation efficiency without adding operational staff.

14. Cell Compaction H3 New

H3 functions: compactCells(cellSet) and uncompactCells(compactedSet, res)

What it is: When you convert a large geofence polygon to H3 cells, you might get thousands of small cells. compactCells replaces groups of 7 child cells with 1 parent cell wherever possible — dramatically reducing the cell count while covering the exact same area. uncompactCells reverses it back to fine resolution when needed.

How we use it in GrubData: Geofence zones stored in the geo_zones.h3_cells array. A large restricted zone (like an airport perimeter) could have 5000+ resolution-9 cells. After compaction, that drops to maybe 200 mixed-resolution cells. Smaller storage, faster lookups. When checking a driver ping against a zone, we uncompact only the relevant parent cells.

Where: Geofence zone creation and storage. Also useful for storing large coverage areas efficiently.

flowchart LR
    A["Large geofence polygon\nconverted to 5000+\nresolution-9 cells"] --> B["H3 compactCells\nmerge groups of 7\ninto parent cells"]
    B --> C["Result: ~200 cells\nmixed resolution\nsame area coverage"]
    C --> D["Store in geo_zones\nh3_cells array\n25x smaller"]

    style B fill:#E8F5E9
Library cost: $0. compactCells runs once at zone creation.
Without this: A large geofence zone like Dubai International Airport perimeter = 5,000+ resolution-9 cells stored in a PostgreSQL array. Checking WHERE $cell = ANY(h3_cells) against a 5,000-element array is slow. Multiply by 500K pings/sec = massive CPU waste. Storage: 5,000 × 8 bytes × 500 zones = ~20MB just for cell arrays.
With this: After compaction, 5,000 cells become ~200 mixed-resolution cells. Array lookups are 25x faster. Storage drops to ~0.8MB. Zone check per ping goes from ~50µs to ~2µs.
Efficiency gain: 25x smaller zone storage, 25x faster containment checks. System part affected: geo_zones table, geofence check in ping handler.
At scale (1M boxes): At 500K pings/sec checking 500 zones, compaction saves ~24µs per ping = 12 CPU-seconds per second saved. That's roughly 1–2 fewer server instances ($200–$500/month).

15. Density Normalization H3 New

H3 function: cellArea(cell, unit)

What it is: Returns the exact area of a hex cell in square meters or square kilometers. H3 hexagons are nearly equal in area, but not perfectly — cells near the poles are slightly different from cells near the equator.

How we use it in GrubData: When showing heatmap density, raw event counts can be misleading. A cell with 50 events that covers 0.05 km² is much more dense than a cell with 50 events covering 0.2 km². cellArea lets us normalize: incidents per square kilometer instead of raw count. This gives a fair density comparison across the map.

Where: Dashboard heatmap analytics — converting raw counts to density values for accurate visualization. Also useful for coverage area calculations in reports.

Library cost: $0. Pure math function, runs in microseconds.
Without this: Heatmaps show raw counts — misleading for government reports. "Area X has 50 events" looks the same as "Area Y has 50 events" even if X is 10x smaller. To fix this without H3, you'd need custom spatial area calculations per grid cell, which is complex geometry math.
With this: One function call per cell gives exact area. Divide count by area = true density. Accurate government analytics reports with zero additional cost.
Efficiency gain: Accurate density metrics instead of misleading raw counts. System part affected: dashboard analytics, heatmap rendering, exported reports.

16. Cell-Level Distance H3 New

H3 function: gridDistance(cellA, cellB)

What it is: Returns how many hex "steps" apart two cells are. Not meters — hex steps. If gridDistance is 1, they are direct neighbors. If it's 5, they are 5 hexagons apart. This is way faster than calculating actual geographic distance.

How we use it in GrubData: Quick proximity check without involving PostGIS. "Is this face detection within 3 cells of the previous one?" If yes, they might be related — cluster them. If gridDistance is 50, they are far apart — separate incidents. Also used to determine the k value for gridDisk (how many rings to search for nearby boxes).

Where: Incident clustering logic, nearby search ring calculation, movement path gap detection ("suspect jumped 20 cells — that's suspicious").

Library cost: $0. In-memory integer comparison.
Without this: Every proximity check requires Haversine distance calculation (trig functions) or PostGIS call. At millions of comparisons per second for clustering, that's heavy CPU or DB load.
With this: gridDistance is a single integer comparison — 10,000x faster than geographic distance. Use it as a fast pre-filter, only compute real distance for the few that pass.
Efficiency gain: 10,000x faster proximity checks vs Haversine. System part affected: incident clustering, search result grouping, nearby box k-ring sizing.

17. Cell Validation and Resolution H3 New

H3 functions: isValidCell(cell) and getResolution(cell)

What it is: isValidCell checks if a cell ID is a real H3 cell (not corrupted or garbage data). getResolution tells you what resolution level a cell is at (0-15).

How we use it in GrubData: Input validation. When the frontend sends a cell ID (e.g., for a heatmap click or geofence lookup), we validate it before querying. When processing mixed-resolution data from compacted zones, getResolution tells us which cells need uncompacting. Basic safety — never trust input, always validate.

Where: API input validation middleware, geofence processing, data integrity checks on stored H3 values.

Library cost: $0. Utility functions, nanosecond execution.
Without this: Invalid cell IDs reaching the database cause failed queries, wasted CPU cycles, and potentially incorrect results. Debugging bad H3 data in production is expensive in engineer time.
With this: Catch bad data at the API boundary before it touches the database. Prevents garbage-in-garbage-out. getResolution ensures mixed-resolution data from compacted zones is handled correctly.
Efficiency gain: Prevents downstream errors. System part affected: all API endpoints accepting H3 cell parameters, data migration scripts.

18. Exact Polygon Containment PostGIS New

What it is: Was the driver exactly inside the restricted compound? Not approximately — exactly.

Why PostGIS: H3 gives approximate containment (hex boundaries don't match real zone shapes). PostGIS uses ST_Contains(zone_polygon, driver_point) for precise geometric truth. If a court asks "was this vehicle inside the zone?" — you need PostGIS-level accuracy.

Where in GrubData: Geofence validation (after H3 pre-check), evidence boundary checks, legal-grade location proof.

Library cost: $0. PostGIS is a free extension on our existing PostgreSQL. No new service, no license.
Without this: H3 containment is approximate — a hex cell might overlap the zone boundary. For government/legal evidence, "approximately inside" is not acceptable. Commercial GIS containment services (Esri, Google Maps) charge per API call — at scale, $5,000–$20,000/month.
With this: ST_Contains runs inside our own database. Zero per-query cost. Legally defensible, meter-accurate. Combined with H3 pre-filter (Section 8), PostGIS only runs on 1% of checks.
Efficiency gain: Government-grade accuracy at zero marginal cost. System part affected: geofence validation, evidence reports, audit logs.

22. Route Matching (GPS to Road) Valhalla New

What it is: Raw GPS is noisy. A vehicle reports a position in the middle of a building. Route matching snaps those GPS points to the nearest real road, giving you the actual path the vehicle took.

How: Send a batch of GPS pings to Valhalla's trace_route API → get back a road-snapped LineString geometry.

Where in GrubData: New infra/routing.ts HTTP client. Results stored in driver_routes table as PostGIS LineString.

Use cases: Vehicle route truth, evidence-grade path reconstruction, deviation detection input.

Library cost: Valhalla Docker container = ~$50–$150/month compute (t3.medium or equivalent). OpenStreetMap road data = $0 (free download, UAE extract ~200MB).
Without this: Google Roads API for map-matching: $0.01 per request. At 1M drivers × 30 pings/min = 30M requests/hour = $300K/hour = completely impossible at scale. Even at 1K drivers: $300/hour.
With this: Valhalla trace_route handles thousands of requests/sec on a single container. Fixed cost regardless of volume. Process GPS batches in bulk (1 call per route, not per ping).
Efficiency gain: Fixed $150/month vs $300K+/hour on Google. System part affected: new infra/routing.ts, driver_routes table.
At scale (1M boxes): Self-hosted Valhalla at $150/month replaces Google Roads at millions/month. Even adding 3 Valhalla replicas for redundancy = $450/month total.
