1 Executive Summary

Why GrubPac is moving from four separate portals to one unified platform.

Current State

GrubPac operates four independent platforms — GrubAdmin, GrubDelivery, GrubMedical, and GrubHospitality. Each has its own frontend, login, deployment, backups, and maintenance cycle.

Problems

Cost

  • Higher infrastructure spend (4× hosting)
  • Higher maintenance and DevOps effort
  • Duplicate backup and monitoring

Development

  • Same features built four times
  • Same bugs fixed four times
  • Same tests written four times

Operations

  • Four login experiences for users
  • Inconsistent behaviour across portals
  • Slower rollout of new features

Business Risk

  • Harder to onboard new verticals
  • Knowledge split across codebases
  • No single view of a client account

Why Change

Analysis shows 75%–80% of functionality is identical across all four portals. Only 20%–25% is vertical-specific (labels, menus, and a handful of features). Maintaining four codebases for mostly shared logic is not sustainable.

Benefits of One Platform

  • One codebase — fix once, deploy everywhere
  • One login — portal.grubpac.com for all users
  • One deployment — single release pipeline
  • One backup strategy — simpler disaster recovery
  • Faster verticals — new industries added by configuration, not new apps

3 User Thinking Process

System design starts with the user — not the database.

When a team lead designs this platform, they think top-down:

User↓ Role↓ Workflow↓ Features↓ Modules↓ Permissions↓ Platform 
flowchart TB
    U[Who is the user?] --> R[What is their role?]
    R --> W[What workflow do they follow?]
    W --> F[What features do they need?]
    F --> M[Which modules power those features?]
    M --> P[What permissions are required?]
    P --> PL[How does the platform deliver this?]
Example: A Delivery Manager needs to track GrubPacs at restaurants. User → Manager role → Tracking workflow → Tracking + Maps features → GrubPacs Engine + Groups Engine → Read/Update permissions → Dynamic menu shows only Delivery items.

6 Multi-Tenancy

Every client is a tenant. Data never crosses tenant boundaries.

flowchart TB
    T[Tenant — one client organisation]
    T --> E[Employees]
    T --> G[Groups]
    T --> GP[GrubPacs]
    T --> S[Settings]
    T --> F[Features]
    T --> SUP[Support / FAQs]
    T --> L[Logs & Audit]

tenant_id

Every database row for a client carries tenant_id. Every API request validates tenant context. Users can only access data within their tenant.

Data Separation

  • Row-level isolation by tenant_id
  • API middleware enforces tenant scope
  • Admin impersonation is logged and audited
  • No shared data between clients
Tenant isolation rule: A Delivery client in Mumbai cannot see a Medical client in Delhi. Even on the same platform, they are completely separate.
