Monitoring — all portals and Smart Box

Three separate paths — do not mix them up:

Metrics (numbers: CPU, errors, latency) → Prometheus collects and stores → alerts fire from Prometheus rules.

Logs (text lines: app errors, debug output) → Grafana Alloy collects from apps → sends to Loki for storage and search. Loki does not collect — Alloy does.

Traces (request paths across services) → apps send via OpenTelemetry → Tempo stores them.

All three are viewed together in Grafana dashboards. Only Prometheus triggers automatic alerts.

Metrics path

Smart Box + all portal apps + EC2 → Prometheus collects metrics → Grafana → Command Center

Traces path

All portal apps → OpenTelemetry → Grafana Tempo → Grafana

Logs path

All portal apps → Grafana Alloy collects logs → Grafana Loki stores logs → Grafana

AWS — only where a portal needs it

Any portal → AWS APIs if required → S3 · Rekognition · SQS · PostgreSQL → EC2 Docker

Not every portal needs AWS. GrubData uses S3 and Rekognition today; other portals add services only when their product requires them.

Deploy — any portal code change

GitHub → GitHub Actions → Trivy → Docker build → Amazon ECR → EC2 deploy → All live portals

Alerts — any portal outage

Full step-by-step resolution is in Section 7. Summary:

Smart Box + all portals + EC2 → Prometheus → Alertmanager → OneUptime + Slack + Plane.so → On-call investigates → Fix via GitHub Actions or runbook → Verify in Grafana → Close ticket + BookStack postmortem

7 Incident & On-Call Software — World-Class vs GrubPac

When something breaks, you need two different things: incident software (pages on-call, tracks the outage, publishes status) and team chat (people talk to each other). Slack is chat only — it is not the best incident tool in the world.

Why GrubPac uses OneUptime instead of PagerDuty or Incident.io: Same job — track outages, page on-call, show a public status page — but free to self-host on our EC2 server. Slack stays for team chat. When the company grows and needs paid support or mobile paging at scale, PagerDuty or Incident.io are the industry leaders to consider.

Full incident flow — from detection to closed ticket

Same flow for every portal outage. Alerts start from Prometheus metrics only. Logs (Loki) and traces (Tempo) are used later to investigate — see Section 4 for all three paths.

Step 0 — Where data comes from (top of the flow)

Metrics → Prometheus (this path triggers alerts)

GrubPac Smart Box · All portal apps · EC2 server → Prometheus collects metrics

Logs → Alloy → Loki (parallel path — used in Step 4 investigation, not for auto-alerts)

All portal apps write logs → Grafana Alloy collects → Grafana Loki stores

Smart Box sends GPS, health, connectivity metrics to Prometheus. Portal apps send metrics (errors, latency) to Prometheus and log lines to Alloy. EC2 sends CPU, memory, disk metrics to Prometheus. Prometheus checks rules every few seconds — when a metric breaks a limit, Step 1 starts.

Step 1 — Detect

Metric goes bad → Prometheus alert rule fires → Alertmanager routes alert

Example: portal response time too slow, box offline, EC2 disk full, or error rate above limit — Prometheus compares live metrics to rules and triggers an alert.

Step 2 — Notify (three places at once)

Alertmanager → OneUptime opens incident · Slack notifies team · Plane.so creates ticket

OneUptime = official incident record + public status page + pages on-call. Slack = team talks in a channel. Plane.so = work ticket so nothing is lost.

Step 3 — After ticket is raised: triage and assign

On-call acks in OneUptime → Plane.so ticket assigned to on-call engineer → Slack incident channel — team joins → BookStack runbook opened

P1/P2: Engineering Manager and CTO notified in Slack. P1: Field Ops alerts customers via ERPNext + Slack. Severity table below.

Step 4 — Investigate root cause

On-call opens Grafana · Loki for logs · Tempo for traces → Root cause found

Notes go into Plane.so ticket and Slack thread so the whole team sees progress.

Step 5 — Fix the problem

Code bug? → GitHub PR → GitHub Actions → ECR → EC2 deploy or rollback
Config or server issue? → Fix on EC2 using BookStack runbook → Update Plane.so ticket with what changed
Field or customer issue? → ERPNext field ticket → Field Ops via GrubAdmin + Slack

Step 6 — Verify fix worked

Prometheus metrics back to normal → Grafana confirms recovery → On-call monitors 15 min

Step 7 — Close incident and ticket

OneUptime incident marked resolved → Status page updated → Plane.so ticket moved to Done → Slack — resolved announcement

Step 8 — After close: postmortem and records

BookStack postmortem written → OneUptime incident closed → Govt SLA Reporter logs downtime if contract portal → Command Center shows green again
